# Skill: make-plan

> **元组**：rule（待创建，可选）+ skill `make-plan`（本文件，行动计划制作流程）
> **定位**：制作行动计划方案。行动方案的本质是**一次完整的repo更新行为**——未来要更新系统的文档和代码。这些更新需要AI提前获得充分但不过载的认知，为此必须利用好看法索引文件（甚至新建），确保AI能成功更新repo。更新不只是更新数据，更要更新元数据——对任何文档和代码的更新，都要查映射数据库，看哪些看法索引文件依赖了它，是否需要更新对应的看法索引文件的内容。

## 系统演进逻辑

```
行动方案 = 一次完整的repo更新行为
  ↓
repo更新的本质 = 更新系统的文档和代码
  ↓
更新文档和代码需要AI提前获得充分但不过载的认知
  ↓
为此发明了基于看法索引文件的三层AI认知管理体系
  ↓
方案中利用/新建看法索引文件，目的是确保AI能成功更新repo
  ↓
更新不只是更新数据，更要更新元数据
  ↓
对任何文档和代码的更新，都要查映射数据库（view-index.db）
  ↓
看哪些看法索引文件依赖了它？是否需要更新对应的看法索引文件？
```

## 什么时候被调用

- 用户说"make-plan"/"做计划"/"制定方案"时
- 用户要求开始一个新工作包（WP）时
- 用户要求开始一个新阶段的工作时
- 任何需要制定多步骤行动方案时

## 核心原则

**行动方案 = 一次完整的repo更新行为**。一个完整的行动方案必须包含三个层面：

1. **执行步骤**——要更新哪些文档和代码？怎么更新？（数据更新）
2. **需求追踪与工作包**——为什么更新？更新对应哪个需求点？在整体进度中的位置？（过程管理）
3. **认知准备 + 元数据更新**——执行时AI需要什么认知？更新后哪些看法索引文件需要同步更新？（认知管理）

缺任何一个，执行时都会出问题：
- 缺执行步骤 → 不知道要更新什么
- 缺需求追踪 → 做完不知道验证什么
- 缺工作包管理 → 不知道在整体进度中的位置
- 缺认知准备 → 执行时AI不知道该加载哪些看法文件，三层架构断裂，在认知不充分的情况下工作
- **缺元数据更新 → 更新了文档/代码但没更新看法索引文件，下次AI按看法文件加载时得到的是过时信息，认知体系失效**

## 操作流程

### 步骤1：理解任务，制定执行步骤

分析用户要求，制定具体的执行步骤。核心问题是：**这次要更新哪些文档和代码？怎么更新？**

**产出**：执行步骤清单，每步精确到可验证的粒度，明确标注每步会改动哪些文件。

### 步骤2：更新需求追踪（checklist）

**如果项目有 `checklist/` 目录**（按需求点管理的项目）：

1. **找到当前工作对应的需求点**——在 `checklist/README.md` 的门类索引中找到相关的checkpoint
2. **更新对应checkpoint的状态**——从"未开始"到"进行中"，或记录工作进展
3. **如果没有对应的checkpoint**——判断是否需要新建checkpoint。用 `python3 scripts/generate_checkpoint.py <编号>` 生成模板，填写需求描述和验证方法
4. **在checkpoint中记录涉及的文档和代码**——更新"涉及的文档和代码"字段，指向本次工作会改动的文件

**如果项目没有 `checklist/` 目录**：跳过此步骤，但考虑是否需要建立需求追踪机制。

### 步骤3：更新工作包管理（working-packages）

**如果项目有 `working-packages/` 目录**：

1. **找到当前工作对应的工作包**——在 `working-packages/INDEX.md` 中找到相关的WP
2. **更新WP状态**——从"未开始"到"进行中"，或记录子步骤完成情况
3. **如果没有对应的WP**——判断是否需要新建WP。新建WP文件，更新INDEX.md
4. **在WP中引用相关的checkpoint**——建立WP和需求点的关联

**如果项目没有 `working-packages/` 目录**：跳过此步骤，但考虑是否需要建立工作包管理机制。

### 步骤4：认知准备——为执行时的AI准备好认知加载路径

**这是最关键的步骤**。行动方案的本质是更新repo，而更新repo需要AI提前获得充分但不过载的认知。为此必须在计划阶段就利用好看法索引文件。

1. **列出每个执行步骤需要的视角**——逐个执行步骤思考："做这一步时，AI需要从什么视角理解项目？"

   格式：
   ```
   步骤1：修改continuation_control.py
     → 需要源码分类法（了解continuation_control.py的实现）
     → 需要运行操作分类法（了解控制命令的用法）
     → 需要设计决策分类法（了解为什么这样设计续传机制）
   
   步骤2：更新检查脚本
     → 需要运行操作分类法（了解检查规范）
     → 需要源码分类法（了解脚本结构）
   ```

2. **检查每个视角的看法文件是否存在**——对照README.md的分类法索引
   - 看法文件已存在 → 确认它索引了执行步骤需要的文档/代码（用 `query-by-view` 查询）
   - 看法文件不存在 → **提前创建它**（按read-sync skill的"新建看法文件"流程）
   - 看法文件存在但不完整 → **补充它**（加入缺失的文档/代码描述，同步更新映射数据库）

3. **提前准备新的看法文件**——如果当前工作引入了新的知识资产（新文档、新代码模块、新数据结构），判断是否需要新建分类法或更新现有看法文件：
   - 执行分类法决策树（见read-sync skill步骤2B）
   - 如果新建分类法：在README.md中加分类法条目，创建看法文件，更新映射数据库
   - 如果更新现有看法文件：加入新资产描述，`view_index.py add` 更新映射

4. **更新映射数据库**——认知准备过程中对看法文件的任何变更，都必须同步到 `view-index.db`：
   ```bash
   # 新增映射
   python3 scripts/view_index.py add <taxonomy> <view_file> <asset_path> <asset_type> [title]
   
   # 查询确认
   python3 scripts/view_index.py query-by-view <view_file>
   ```

**产出**：每个执行步骤的认知加载路径清单 + 看法文件准备完成确认。

### 步骤5：元数据更新计划——列出更新后需要同步的看法索引文件

**行动方案不只是更新数据，更要更新元数据。** 每个执行步骤会改动文档/代码，改完后必须查映射数据库，看哪些看法索引文件依赖了被改动的文件，是否需要更新对应的看法索引文件的内容。

1. **列出每个执行步骤会改动的文件**——从步骤1的执行步骤中提取

2. **对每个会改动的文件，查映射数据库**：
   ```bash
   python3 scripts/view_index.py query-by-asset <被改动的文件路径>
   ```
   查出这个文件被哪些看法文件索引了。

3. **判断每个看法文件是否需要更新**——文件被改动后，它在看法文件中的描述（讲什么/覆盖问题场景/依赖关系）是否还准确？
   - 描述仍然准确 → 不需要更新
   - 描述不再准确 → **列入元数据更新清单**，执行完成后更新该看法文件中对应条目的描述

4. **产出元数据更新清单**：
   ```
   步骤1会改动：monitoring/continuation_control.py
     → 被 [源码] src/README.md 索引 → 需要更新描述（控制命令新增了X）
     → 被 [运行操作] docs/specs/README.md 索引 → 需要更新描述（控制命令用法变化）
   
   步骤2会改动：scripts/monitor_check_continuation.sh
     → 被 [运行操作] docs/specs/README.md 索引 → 需要更新描述（检查逻辑变化）
   ```

**这个清单是执行完成后的元数据更新待办事项。**

### 步骤6：整合行动计划

将步骤1-5的产出整合为一份完整的行动计划：

```markdown
# <工作名>行动计划

## 执行步骤
1. <步骤1> — 会改动：<文件列表>
2. <步骤2> — 会改动：<文件列表>
...

## 需求追踪
- 对应checkpoint：<编号> — <标题>
- 验证方法：<从checkpoint中引用>

## 工作包管理
- 对应WP：<编号> — <标题>
- WP状态更新：<从X到Y>

## 认知准备
### 步骤1需要的视角
- <分类法1> → 看法文件：<路径> → 需要加载：<文件列表>
- <分类法2> → 看法文件：<路径> → 需要加载：<文件列表>

### 步骤2需要的视角
- ...

### 看法文件准备状态
- <看法文件1>：已存在，完整 ✓
- <看法文件2>：已补充，新增<N>个条目 ✓
- <看法文件3>：新建完成 ✓
- 映射数据库：已同步 ✓

## 元数据更新计划（执行完成后）
### 步骤1完成后
- <文件1> → 被 [源码] src/README.md 索引 → 更新描述：<变更内容>
- <文件1> → 被 [运行操作] docs/specs/README.md 索引 → 更新描述：<变更内容>

### 步骤2完成后
- <文件2> → 被 [运行操作] docs/specs/README.md 索引 → 更新描述：<变更内容>
```

### 步骤7：落盘并commit

1. **行动计划落盘**——如果是有一定规模的工作，行动计划记录到 `dev-docs/` 下带编号的文档中
2. **checklist/working-packages更新落盘**——commit需求和工作包的状态变更
3. **看法文件更新落盘**——commit看法文件和映射数据库的变更
4. **README.md更新落盘**——如果新建了分类法，commit README.md的变更

## 执行完成后的元数据更新（必须执行）

**执行行动计划后，必须按步骤5的元数据更新清单，更新对应的看法索引文件。**

1. 对每个被改动的文件，确认改动已完成
2. 按元数据更新清单，更新对应看法文件中该文件的描述（讲什么/覆盖问题场景/依赖关系）
3. 如果改动导致文件不再属于某个分类法，从看法文件中移除，`view_index.py remove` 删除映射
4. 如果改动导致文件新属于某个分类法，加入看法文件，`view_index.py add` 添加映射
5. 同步映射数据库
6. commit元数据更新

**不更新元数据 = 下次AI按看法文件加载时得到过时信息 = 认知体系失效 = 三层架构断裂**

## 设计原则

1. **行动方案 = 一次完整的repo更新行为**——不只是"执行步骤"，是数据更新+过程管理+认知准备+元数据更新的完整闭环
2. **认知准备是前置条件**——执行前必须为AI准备好认知加载路径，利用好看法索引文件（甚至新建），确保AI能成功更新repo
3. **看法文件提前准备**——如果执行需要新的视角或新的文档索引，在计划阶段就创建/更新看法文件，不在执行中临时补
4. **元数据更新是后置条件**——执行完成后必须更新看法索引文件和映射数据库。更新了数据但不更新元数据 = 认知体系失效
5. **映射数据库是双向跟踪的核心**——认知准备时用 `query-by-view` 确认看法文件完整；元数据更新时用 `query-by-asset` 查哪些看法文件依赖了被改动的文件
6. **按项目实际情况调整**——如果项目没有checklist/working-packages目录，跳过对应步骤，但认知准备和元数据更新步骤不可跳过
