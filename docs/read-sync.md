# Skill: read-sync

> **元组**：rule `readme-context-guard.md`（always-on触发）+ skill `read`（使用引导地图）+ skill `read-sync`（本文件，创建/维护引导地图）
> **定位**：创建或维护repo的README.md**完整项目认知地图**，并用映射数据库双向跟踪看法文件与文档/代码/资产的映射关系，同时维护trace.csv的资产追溯关系幂等性。README.md不只是"当前文档体系的引导地图"，而是"下一个AI读完就能理解项目来龙去脉的完整认知地图"——包括当前结构是什么、为什么是这个结构、做过哪些决策、否决过哪些方案。当repo的文档体系发生变化时（新增外移文档、现有文档内容定位变化、文档被删除或合并、目录结构重组），用本skill同步更新README.md、看法文件、映射数据库，**以及trace.csv中的追溯关系**。

## 什么时候被调用

- 用户说"read-sync"/"同步readme"/"更新readme"/"维护readme"时
- repo中新增外移文档后
- 现有外移文档的内容定位发生变化后
- 文档被删除或合并后
- 新repo需要建立README.md引导地图时
- AGENTS.md瘦身工程完成后需要建立引导地图时

> **幂等维护意识（重要）**：用户发起 read-sync 时，**不只是要求维护README.md和看法文件**，同时要求AI**主动思考trace.csv的幂等更新**。AI必须看着当前上下文（本次session做了什么变更）和git log（最近的commit改了什么），判断trace.csv需要哪些幂等更新。详见步骤2C。

## 操作流程

### 步骤1：确定当前状态

判断当前是"创建"还是"维护"：

- **创建**：repo根目录没有README.md，或README.md不是引导地图（是其他用途的README）
- **维护**：repo根目录已有README.md引导地图（开头有"强制声明：AI必须确保本文件内容在自己的上下文中..."）

### 步骤2A：创建认知地图

如果是创建，按三层架构生成README.md和看法文件。

**三层架构**：
- **第一层 AGENTS.md** — 铁律 + 最小索引（always-on）
- **第二层 README.md** — 分类法索引（AI判断"需要哪种视角"）
- **第三层 看法文件** — 某种视角下的文档/代码/资产索引（AI判断"需要加载哪些具体文档"）

**README.md（第二层）结构**：
```markdown
# README.md — 项目认知地图

> **强制声明**：AI必须确保本文件内容在自己的上下文中，才能回答用户的问题或进行后续操作。如果上下文中没有本文件的完整内容，必须先用read工具完整加载本文件，然后再回答问题或操作。
>
> 本文件是分类法索引——索引"有哪些视角可以看这个项目"。AI读完本文件后，判断"我当前的问题需要哪种视角"，然后加载对应的看法文件（第三层），再判断"需要加载哪些具体文档"。

## 分类法索引

本项目可以从以下N种视角理解。每种视角是一个"分类法"——对同一批知识的不同组织方式。判断你当前的问题需要哪种视角，加载对应的看法文件。

### 1. <分类法名> — "<视角一句话>"
<视角描述2-3句：这个分类法从什么角度看项目，加载能得到什么>
**看法文件**：`<看法文件路径>`
**覆盖场景**：<列出哪些问题/任务需要用这个视角>

### 2. <分类法名> — "<视角一句话>"
...

## 附录：快速开始与Git历史
...
```

**README.md只索引分类法，不描述具体文档**。具体文档的描述在看法文件中。

**看法文件（第三层）结构**：
```markdown
# <分类法名> — <视角一句话>

> **加载本文件能得到什么**：<这个视角下能看到什么，2-3句>

## 索引的文件

### `<文件路径>` — <一句话标题>

<这个文档讲什么，2-3句>

**覆盖问题场景**：
- <场景1>
- <场景2>

**依赖关系**：<加载本文件后可能还需要加载什么>
```

**创建流程**：
1. 调查repo的全部知识资产（代码、文档、数据、需求、工作包、变更历史）
2. 识别有哪些视角可以看这些资产——每种视角是一个分类法
3. 为每个分类法创建看法文件（第三层）
4. 创建README.md索引所有分类法（第二层）
5. 确保AGENTS.md有指向README.md的强制声明（第一层）
6. **建立映射数据库**（见"映射数据库"节）——双向跟踪看法文件与文档/代码/资产的映射关系

**分类法的识别原则**：
1. 一个分类法必须能索引**一批**文档/代码/资产——只覆盖一个文档的不够独立成分类法
2. 分类法之间可以重叠——同一个文档可以被多个分类法索引（视图重叠是正常的）
3. 常见分类法参考：系统认知（是什么）、设计决策（为什么这样设计）、需求（要满足什么）、源码（怎么实现）、工作流（怎么推进）、运行操作（怎么运行）、历史（怎么演变）
4. 按repo实际情况识别，不强制套用参考列表

### 步骤2B：维护认知地图

如果是维护，按变更类型执行。维护的核心是**分类法意识**——遇到任何文档/知识变化时，先判断它属于哪种看法（分类法），然后决定是更新既有看法文件还是新建分类法。

#### 分类法决策树（遇到新文档/新知识时必须执行）

```
新文档/新知识出现
  ↓
第1步：它讲什么？属于哪种视角？
  ↓
对照README.md中的分类法索引——逐个判断这个新内容是否匹配某个现有分类法的视角
  ↓
第2步：是否匹配某个现有分类法？
  ├─ 是 → 更新该分类法的看法文件（加一段描述）
  │       如果该分类法还没有看法文件，先创建它（见"新建看法文件"流程）
  └─ 否 → 第3步
  ↓
第3步：它是否代表一种新的视角？
  判断标准——这种视角是否能索引一批文档/代码/资产，而不只是这一个文档？
  ├─ 是，能索引一批 → 新建分类法（README.md加一段+创建看法文件）
  └─ 否，只索引这一个 → 归入最接近的现有分类法，更新其看法文件
```

**关键判断标准**：一个分类法必须能索引**一批**文档/代码/资产，不能只索引一个。如果一个新视角只能覆盖一个文档，它不够独立成分类法，应该归入最接近的现有分类法。

**分类法意识的核心**：不是每个新文档都需要新建分类法。大多数新文档应该归入现有分类法——更新对应的看法文件即可。只有当新文档代表了一种全新的、能覆盖一批知识的视角时，才新建分类法。

#### 变更类型处理

**新增外移文档时**：
1. 执行分类法决策树——判断属于哪个分类法
2. 如果匹配现有分类法：更新该分类法的看法文件（加一段描述：文件名/讲什么/覆盖问题场景/依赖关系）
3. 如果新建分类法：在README.md中加一段分类法描述（视角/能得到什么/看法文件路径），创建看法文件
4. 检查其他分类法的看法文件是否需要追加指向新文档（视图重叠）

**现有文档内容定位变化时**：
1. 执行分类法决策树——判断变化后的内容是否仍属于原分类法
2. 如果仍属于原分类法：更新该分类法看法文件中对应文档的描述
3. 如果变化后属于不同分类法：从原看法文件移除，加入新分类法的看法文件
4. 更新"覆盖问题场景"和"依赖关系"

**文档被删除或合并时**：
1. 从所有引用它的看法文件中移除对应描述
2. 检查其他文档的"依赖关系"是否有指向被删除文档的引用，移除这些引用
3. 如果文档被合并到另一个文档，更新合并目标文档在看法文件中的描述
4. 检查是否有分类法因此变得空了（不再索引任何文档）——如果是，考虑合并到最接近的分类法或删除该分类法

**目录结构重组时**：
1. 重组通常影响多个分类法——逐个检查每个看法文件中的路径引用是否需要更新
2. 如果重组产生了新的目录结构，判断是否需要新建分类法（如"checklist拆分"产生了"需求分类法"）
3. 重组方案记录到历史分类法（dev-docs/）
4. **映射数据库批量更新**——重组会改变大量路径，用 `view_index.py remove` 删除旧路径映射，`view_index.py add` 添加新路径映射

#### 映射数据库同步（每次变更后必须执行）

**核心原则**：看法文件和映射数据库是同一事实的两个表达——看法文件是人/AI可读的描述，映射数据库是机器可查询的索引。两者必须保持一致。**改了看法文件就必须同步映射数据库，反之亦然。**

**映射数据库的作用**：
- **文档/代码变更时**：`query-by-asset <path>` 查出哪些看法文件需要更新——不用人工记忆"这个文件被哪些看法索引了"
- **看法文件要更新时**：`query-by-view <view_file>` 查出它索引了哪些文档/代码——确保看法文件内容完整，不遗漏
- **验证一致性时**：对比数据库中的映射和看法文件实际描述的文档，发现遗漏或多余

**同步操作**：
```bash
# 新增映射（文档加入某看法文件时）
python3 scripts/view_index.py add <taxonomy> <view_file> <asset_path> <asset_type> [title]

# 删除映射（文档从某看法文件移除时）
python3 scripts/view_index.py remove <view_file> <asset_path>

# 查询：某文档变更时，哪些看法文件需要更新
python3 scripts/view_index.py query-by-asset <asset_path>

# 查询：某看法文件索引了哪些文档
python3 scripts/view_index.py query-by-view <view_file>

# 统计
python3 scripts/view_index.py stats
```

**asset_type 取值**：`document`（文档）、`code`（代码）、`script`（脚本）、`data`（数据）

#### 新建看法文件

当分类法决策树判定需要新建分类法时，创建看法文件：

**看法文件结构**：
```markdown
# <分类法名> — <视角一句话>

> **加载本文件能得到什么**：<这个视角下能看到什么，2-3句>
> **看法文件位置**：<文件路径>

## 索引的文件

### `<文件路径>` — <一句话标题>

<这个文档讲什么，2-3句>

**覆盖问题场景**：
- <场景1>
- <场景2>

**依赖关系**：<加载本文件后可能还需要加载什么>
```

**看法文件放置位置**：优先放在该分类法对应的知识目录下。如"需求分类法"的看法文件放 `checklist/README.md`，"工作流分类法"放 `working-packages/README.md`。如果没有自然归属的目录，新建一个。

**看法文件和README.md的关系**：README.md只保留每个分类法的一段描述（视角/能得到什么/看法文件路径），具体文档的描述在看法文件中。README.md是分类法索引，看法文件是文档索引。

**AGENTS.md瘦身工程完成后**：
1. 瘦身工程会把AGENTS.md的内容外移到多个独立文件
2. 瘦身完成后，用步骤2A的流程为这些外移文件创建引导地图
3. 在AGENTS.md中添加强制声明指向README.md

### 步骤2C：幂等追溯关系检查与更新（每次维护必须执行）

**核心意识**：read-sync 不只维护认知地图（README.md + 看法文件 + view-index.csv），还要维护追溯关系（trace.csv）。认知地图和追溯关系是两个维度的幂等性——认知地图是"文档怎么被索引"，追溯关系是"资产之间有什么关系"。**两者都必须同步，才算完整的 read-sync。**

**触发条件**：每次执行 read-sync 维护（步骤2B）时，必须同时执行步骤2C。无论是用户主动发起 read-sync，还是AI在文档变更后自动维护，都要检查 trace.csv 是否需要更新。

**操作流程**：

#### 2C-1：收集变更证据

从两个来源收集本次需要同步的变更：

**来源A：当前上下文（本次session做了什么）**
- 回顾本次session中创建/修改/删除了哪些文件
- 这些文件属于什么资产类型（code/document/checkpoint/wp/dev-doc/script/config/template/db-collection/runtime-asset）

**来源B：git log（最近的commit改了什么）**
```bash
# 查看最近的commit（本次session的commit）
git log --oneline -20

# 查看最近commit改动的文件
git log --name-only -5
```

#### 2C-2：判断需要哪些幂等更新

对照以下检查清单，判断trace.csv需要哪些更新：

| 变更类型 | 需要更新的trace.csv关系 | 判断方法 |
|---|---|---|
| 新增代码文件 | `contains`（文件→函数）、`changed-in`（文件→commit） | 新文件是否有def/class？新文件在哪个commit中添加？ |
| 新增文档文件 | `contains`（文件→章节）、`changed-in`（文件→commit） | 新文档是否有##章节？新文档在哪个commit中添加？ |
| 新增checkpoint | `implements`/`specified-by`/`part-of` | 新checkpoint实现了什么代码？由什么文档规范？属于哪个WP？ |
| 新增wp | `comes-from`（wp→dev-doc）、`creates`（wp→checkpoint） | 新WP来自哪个方案？创建哪些checkpoint？ |
| 新增dev-doc | `produces`/`changes`（dev-doc→document/code） | 新dev-doc产出/改动了什么文件？ |
| 新增脚本 | `changed-in`（脚本→commit） | 新脚本在哪个commit中添加？ |
| 新增配置/模板 | `configures`/`uses-template` | 新配置被哪些代码引用？新模板被哪些launcher使用？ |
| 新增DB collection | `reads-from`/`writes-to`（code→db-collection） | 新collection被哪些代码读写？ |
| 新增运行资产 | `generates`（code→runtime-asset） | 新运行资产被哪些代码引用？ |
| 新增commit | `changed-in`（资产→commit） | 新commit改动了哪些文件？ |
| 新增看法文件 | `indexes`（view-file→资产）、`organizes`（README→view-file） | 新看法文件索引了哪些资产？ |
| 文件被删除 | 移除相关关系 | 被删除文件的所有关系都应移除 |
| 文件内容变化 | `contains`关系可能需要更新 | 函数/章节增减？ |

#### 2C-3：执行幂等更新

根据2C-2的判断结果，执行更新：

```bash
# 查看当前trace.csv状态
python3 scripts/trace.py stats

# 查看某资产现有关系（确认是否需要更新）
python3 scripts/trace.py query <type> <id>

# 录入新关系
python3 scripts/trace.py add <s_type> <s_id> <t_type> <t_id> <relation> [note] [commit_id]

# 移除过期关系（文件被删除时）
python3 scripts/trace.py remove <s_type> <s_id> <t_type> <t_id> <relation>

# 批量录入（如果有多个同类关系要录入，用对应的录入脚本）
python3 scripts/trace_contains.py      # contains关系（函数级/章节级）
python3 scripts/trace_checkpoints.py   # checkpoint关系
python3 scripts/trace_wp_devdoc.py     # dev-doc/wp关系
python3 scripts/trace_commits.py       # changed-in关系
python3 scripts/trace_infra.py         # DB/配置/模板/运行资产关系
python3 scripts/trace_view_file.py     # view-file关系
```

**注意**：录入脚本是全量重扫的（会跳过已存在的关系），适合大批量更新。对于少量新增关系，直接用 `trace.py add` 逐条录入更高效。

#### 2C-4：验证幂等性

更新完成后，验证trace.csv的幂等性：

```bash
# 重新生成资产清单（如果repo结构有变化）
python3 scripts/enumerate_assets.py

# 验证覆盖率
python3 scripts/trace_verify.py
```

**验证标准**：
- 资产覆盖率100%（无孤立资产）
- 本次session新增的资产都有至少一条关系
- 本次session涉及的commit都有changed-in关系

**如果验证不通过**：根据 `scripts/orphan_assets.csv` 中的孤立资产清单，逐个补全关系。

#### 2C-5：commit幂等更新

幂等更新和认知地图更新一起commit，或单独commit：
```
更新README.md引导地图 + trace.csv幂等同步：<变更原因>（read-sync skill）
```

### 步骤3：验证完整性

维护/创建完成后，验证：

1. **三层架构检查**——
   - 第一层：AGENTS.md有指向README.md的强制声明
   - 第二层：README.md是分类法索引，不描述具体文档（每个分类法一段描述+看法文件路径）
   - 第三层：每个分类法有对应的看法文件，看法文件描述具体文档
2. **分类法覆盖性检查**——README.md中的每个分类法是否有对应的看法文件？看法文件是否存在？
3. **文档覆盖性检查**——repo的所有文档/代码/资产是否被至少一个分类法的看法文件索引？
4. **映射数据库一致性检查**——看法文件和映射数据库是否一致？
   - 对每个看法文件：`query-by-view <view_file>` 查出的文档列表，是否和看法文件实际描述的文档一致？
   - 看法文件中描述了但数据库中没有的文档 → 补充映射（`add`）
   - 数据库中有但看法文件中没有描述的文档 → 补充描述到看法文件，或从数据库删除映射（`remove`）
5. **依赖关系检查**——每个文档的"依赖关系"中引用的文档是否存在
6. **场景描述检查**——每个文档的"覆盖问题场景"是否准确反映当前文档内容
7. **认知完整性检查**——下一个AI读完README.md能否理解项目的来龙去脉？具体检查：
   - **变更历史是否被引导**——是否有"历史分类法"索引dev-docs/等方案记录？
   - **决策溯源是否可达**——当前结构的关键设计决策，下一个AI能否找到决策过程和否决方案？
   - **认知盲区识别**——问自己"如果我是新接手的AI，读完README.md后遇到'要不要改结构'类问题时，我知道去哪里找历史决策吗？"如果不知道，就是认知盲区
   - **分类法盲区识别**——问自己"如果我是新接手的AI，遇到一个新问题，我能否从README.md的分类法索引中找到合适的视角？"如果找不到合适的视角，可能需要新建分类法
8. **trace.csv幂等性检查**——本次read-sync涉及的变更是否已在trace.csv中同步？具体检查：
   - 本次session新增的资产是否都有至少一条trace.csv关系？（`python3 scripts/trace_verify.py`）
   - 本次session涉及的commit是否都有changed-in关系？
   - 被删除文件的关系是否已从trace.csv移除？
   - 如果repo有幂等追溯分类法（`views/idempotency.md`），本次变更涉及的文件是否已在看法文件中描述？

验证方法：
```bash
# 列出repo根目录所有外移文档
ls *.md | grep -v AGENTS.md | grep -v README.md

# 列出所有子目录的文档
find docs/ checklist/ working-packages/ dev-docs/ src/ monitoring/ -name "*.md" | sort

# 对照README.md中的分类法条目（第二层）
grep "^### [0-9]" README.md
```

## 设计原则总结

1. **三层架构**——AGENTS.md（铁律+最小索引）→ README.md（分类法索引）→ 看法文件（文档索引）。各层各司其职，不越层。README.md只索引分类法，看法文件才描述具体文档
2. **分类法是视图，不是分区**——同一个文档可以被多个分类法索引，视图重叠是正常的。分类法是对同一批知识的不同组织方式，就像数据库的视图
3. **分类法意识是维护的核心**——遇到新文档/新知识时，必须执行分类法决策树：判断属于哪个现有分类法→更新其看法文件；还是代表新视角→新建分类法。大多数新文档应归入现有分类法，只有能索引一批知识的新视角才新建分类法
4. **一个分类法必须能索引一批文档/代码/资产**——只覆盖一个文档的不够独立成分类法，应归入最接近的现有分类法
5. **README.md是完整的项目认知地图**——不只是"当前有哪些文档"，还要让下一个AI理解"为什么是现在这个结构、做过哪些决策、否决过哪些方案"
6. **三要素必须齐全**——看法文件中每个文档的描述必须包含：讲什么/覆盖问题场景/依赖关系
7. **维护和创建同等重要**——文档体系变化后不更新认知地图 = AI找不到需要的文档或不知道历史决策
8. **变更历史是认知完整性的关键维度**——必须有"历史分类法"索引dev-docs/等方案记录，否则下一个AI遇到"要不要改结构"时会重新提议已否决的方案
9. **验证必须包含三层架构检查和认知完整性检查**——不只是文件覆盖性和依赖关系，还要检查三层结构完整性和"下一个AI读完能否理解项目的来龙去脉"
10. **映射数据库双向跟踪**——看法文件和映射数据库（`view-index.csv`）是同一事实的两个表达：看法文件是人/AI可读的描述，映射数据库是机器可查询的索引。两者必须保持一致——改了看法文件就必须同步映射数据库，反之亦然。文档/代码变更时用 `query-by-asset` 查要更新哪些看法文件；看法文件要更新时用 `query-by-view` 查它索引了哪些文档。**不维护映射数据库 = 双向跟踪断裂 = 文档变更时不知道要更新哪些看法文件**
11. **幂等追溯关系同步维护（2026-08-19确立）**——read-sync 不只维护认知地图（README.md + 看法文件 + view-index.csv），还要维护追溯关系（trace.csv）。认知地图和追溯关系是两个维度的幂等性：认知地图是"文档怎么被索引"，追溯关系是"资产之间有什么关系"。**用户发起 read-sync 时，AI必须主动思考trace.csv的幂等更新**——看当前上下文（本次session做了什么变更）和git log（最近的commit改了什么），判断trace.csv需要哪些更新（新增资产的contains/changed-in关系、新增checkpoint的implements关系、新增看法文件的indexes关系等）。**不维护trace.csv = 追溯关系过时 = 给定commit时间点trace.csv不再是repo状态的精确镜像**。详见步骤2C。
